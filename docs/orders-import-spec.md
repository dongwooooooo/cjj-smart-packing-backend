## 0. MVP 단계 구분

| 단계 | 범위 | 상태 |
| --- | --- | --- |
| **1차 MVP** | 출고지시 수신 서비스 전체(본 문서), 입고·포장 화면 흐름 지원 | 본 문서 대상 |

## 1. 처리 플로우

```
출고지시 배치 (batchId, 주문[주문번호, 배송지역, SKU, 수량])
        │
        ▼
[A1 접수·파싱] ── 요청 자체 결함 ──▶ 400 VALIDATION_ERROR (배치 전체 거부)
        │
        ▼
[A2 주문별 검증] ── 방면 오류 / 재고 부족 ──▶ 거부 목록 (해당 주문만)
        │
        ▼
┌─ 카토나이제이션 ────────────────────────────┐
│ [블록화] 슈퍼블록 생성, 완충재 패딩           │
│ [배치 엔진] extreme point 적재 + 시도 다양화  │
│ [편성 최적화] 통째 시도, 분할, 국소 탐색      │
│      │  초과 치수 ──▶ 거부 목록              │
└────────┬───────────────────────────────────┘
         ├─▶ [라인 배정]  주문의 배송지역 기준
         ▼
[토트 할당] 배송단위 1개당 토트 1개
         ▼
[저장·상태 전이] 단일 트랜잭션
         ▼
[결과 요약 응답]
```

**패키지 구조 [확정]**: 도메인(inbound/outbound/orders/inventory) 분할 유지, 도메인 내부는 controller/service/repository/entity 4계층. 타 도메인 접근은 그 도메인의 service·repository를 직접 호출한다 — 단 쓰기 경로 규칙은 유지: 재고 증감·조회는 inventory의 InventoryService 창구로만, 상품 쓰기는 P1 전용, 배송단위·토트 생성은 U3의 outbound 서비스로.

## 2. A1 — 출고지시 접수 [확정]

```json
POST /api/v1/admin/orders/import
{
  "batchId": "B-0821-1",
  "orders": [
    { "receiptNo": "R-20260821-0001", "regionCode": "SEOUL",
      "orderedAt": "2026-08-21T09:00:00",
      "items": [ { "gtin": "8801234500011", "qty": 3 } ] }
  ]
}
```

응답 (성공 200):

```json
{
  "batchId": "B-0821-1", "orders": 18, "shipments": 22, "splitOrders": 3,
  "rejected": [
    { "receiptNo": "R-20260821-0007", "reason": "INSUFFICIENT_STOCK",
      "detail": { "gtin": "8801234500011", "requested": 5, "available": 2 } }
  ]
}
```

- `orders`·`shipments`·`splitOrders`는 저장에 성공한 것만 센다. 거부 주문은 `rejected`에만 나타난다.
- **같은 배치 재전송**(네트워크 재시도 포함): 주문번호(receiptNo) UNIQUE 제약에 걸려 배치 전체 400. ShipBob도 고유 참조번호로 같은 방식의 방어를 한다 — 별도 멱등 키는 두지 않는다.
- **상용 API 대비 의도적 축약 4개** (근거: docs/research/fulfillment-outbound-api-benchmark.md): 배송지를 지역코드 하나로 대체(상용은 전체 주소 객체), 상품 식별 GTIN 단독(상용은 판매자 SKU 주 식별), 배송 방식 필드 없음, 응답에 성공 주문 식별자 미반환. 전부 시연 범위 결정이다.

## 3. A2 — 주문 검증 [확정]

2층 구조. 1층은 요청 오류(전체 거부), 2층은 주문별 거부(부분 성공).

### 1층 — 배치 전체 400 `VALIDATION_ERROR`

| 케이스 | 조건 |
| --- | --- |
| 필수 필드 누락 | batchId, receiptNo, regionCode, items 등 없음 |
| 수량 결함 | qty ≤ 0 |
| 빈 주문 | orders 또는 items가 빈 배열 |
| 미등록 바코드 | GTIN이 상품 마스터에 없음 — 시연 가정 밖 입력이므로 요청 오류 취급. **상용 API(Shopify 등)는 건별 거부가 표준이나, 시연 데이터를 통제하므로 의도적으로 전체 거부** |

### 2층 — 주문별 거부 (rejected 노출, 저장 안 함)

| 사유 코드 | 조건 | detail |
| --- | --- | --- |
| `UNKNOWN_REGION` | regionCode가 지역 기준정보에 없음 | regionCode |
| `INSUFFICIENT_STOCK` | 배치 내 주문 순서대로 SKU별 수량을 누적했을 때 현재 재고 초과. 주문 단위 전체 거부 — 부분 출고 없음 | gtin, requested, available |
| `OVERSIZED_ITEM` | 낱개 하나가 카탈로그의 **어떤 박스에도** 안 들어감 (4-3 선검사) | gtin |

- 재고 실차감 없음 — 차감은 포장완료 시점(기존 결정 유지). 여기서는 할당 가능 여부만 판단.
- 거부 주문은 주문 레코드 자체를 만들지 않는다. 거부 주문의 수량은 배치 내 누적에도 넣지 않는다.
- detail 의미: `requested` = 이 주문이 요구한 수량, `available` = 같은 배치의 앞선 통과 주문 반영 후 잔여량.
- 검사 순서는 지역 → 재고 고정. 둘 다 어긋나면 `UNKNOWN_REGION`이 나오고, 지역이 틀린 주문은 재고 누적에 잡히지 않는다.
- 한 주문 안에 같은 GTIN이 여러 줄로 오면 합산해서 판단한다 — 줄 분할로 검사를 피하는 입력 차단.

## 4. 카토나이제이션 [확정]

주문의 전체 블록을 **어떻게 나누고 + 어떤 방향으로 + 어느 박스들에 쌓는가**를 한 문제로 푼다. 나누기(배송단위 편성)와 쌓기(박스 판정)를 분리하지 않는다 — 나누는 방식 자체가 최적화 대상.

### 4-0. 목적함수 [확정]

```
1순위: 박스(배송단위) 개수 최소
2순위: 동점이면 선택된 박스들의 총 부피 최소
```

### 4-1. 블록화

- 상품은 직육면체 블록으로 취급한다. 사이 공간을 채우는 변형은 고려하지 않는다 (형상 데이터 없음 — 실제보다 보수적인 방향의 근사)
- **슈퍼블록 — 보류**: 같은 SKU를 격자 블록으로 합치는 최적화는 구현하지 않았다. 배치 엔진이 동일 블록을 바닥·안쪽 우선 순서로 놓으면 자연히 격자가 되어, 판정 결과가 달라지는 케이스를 만들지 못했다 (테스트로 미실증). 배치 계산이 느려지는 게 실측되면 성능 최적화로 도입
- **완충재 패딩**: 파손주의 SKU 블록은 각 변에 완충재 두께×2(양쪽)를 더한 치수로 취급한다. 배치 기반 판정이라 부피 곱 보정이 아니라 치수 가산이 맞다
- **직립 전용 제약 — 기각**: 모든 블록은 6방향 회전 허용. 눕히면 안 되는 상품은 애초에 배송 상품으로 들어오지 않는다는 전제

### 4-2. 배치 엔진 — "이 블록들이 이 박스에 들어가는가"

extreme point 방식: 박스 안 배치 가능 지점(놓인 블록들의 모서리가 만드는 후보점)에 블록을 하나씩 놓아보며 실제 배치를 구성한다. 배치가 구성되면 "들어간다" — **들어간다고 판정하면 실제 넣는 방법까지 나오므로 무효 추천이 없다.**

- 유효 내치수(각 변 − 마진 3cm) 기준으로 배치
- 블록 회전: 축 평행 6방향
- **시도 다양화 — 보류**: 투입 순서·회전 우선순위를 바꿔 재시도하는 확장은 구현하지 않았다. 단일 고정 순서(바닥·안쪽 우선, 회전 6방향 순차)가 실패하는 배치 가능 조합을 테스트로 만들지 못했다 — 실패 사례가 나오면 그 케이스를 Red 테스트로 추가하고 도입. 탐색 순서 고정으로 같은 입력이면 같은 결과 (결정성)
- 단일 블록의 박스 통과 여부는 배치 엔진의 6방향 회전 시도로 판정한다 (정렬 비교와 결과 동일 — 별도 선별 단계는 두지 않음)
- 한계: 다양화 휴리스틱이라 "실제로는 들어가는데 못 찾는" 경우가 이론상 남는다. 이 오류는 박스가 한 단계 커지는 방향이지, 안 들어가는 추천이 나오는 방향이 아니다

### 4-3. 편성 최적화

```
1. 통째 시도: 주문 전체 블록이 박스 1개에 들어가는지, 부피 오름차순으로
   → 성공 시 그 박스가 최적 (개수 1, 최소 부피). 대부분의 주문이 여기서 끝
2. 초기 분할: 안 되면 FFD — 블록을 부피 내림차순(동률이면 GTIN 순)으로,
   수용 가능한 첫 배송단위에 배치. 없으면 새 단위
3. 국소 탐색: 단위 간 블록 이동을 시도하고 (맞교환은 개선 사례 발견 시 도입),
   목적함수(개수, 동점이면 총 부피)가 좋아지는 변경만 채택. 개선 없으면 종료
```

- **적층불가 선분리**: 적층불가 SKU는 다른 SKU와 동거 금지, 같은 SKU끼리는 허용. 국소 탐색의 이동 대상에서도 제외
- 하중·적층 순서 규칙은 두지 않는다 — 상품별 내하중 데이터가 없어 검증 불가능한 규칙이 된다. 눌림 위험은 파손주의 플래그와 완충재가 담당
- **초과 치수 선검사**: 시작 전, 어떤 박스에도 안 들어가는 낱개가 있으면 `OVERSIZED_ITEM` 거부. 박스 라인업은 비례 관계가 아니므로(우체국 2호는 1호보다 부피는 커도 한 변이 좁다) 최대 박스 하나가 아니라 전 박스를 검사

### 4-4. 박스 확정

편성 결과의 각 배송단위에 대해, 배치 엔진을 통과한 박스 중 최소 부피 박스 = 추천 박스. 추천값 불변 보존, 작업자 오버라이드는 별도 필드 (기존 계약).

### 4-5. 완충재 표시

배송단위에 파손주의 SKU가 1개 이상이면 완충재 권유 true. 4-1 패딩과 같은 판정에서 파생.

### 4-6. 파라미터

| 파라미터 | 값 | 성격 |
| --- | --- | --- |
| 마진 | 3cm | 확정 (D-11) |
| 완충재 두께 | 1cm (변당 양쪽 +2cm) | 실측 근거 없는 임의값. `packing.filler-thickness-cm` 설정 분리 — 리허설 때 조정 |
| 다양화 시도 수 | 보류 — 단일 고정 순서 (4-2) | 실패 사례 발견 시 도입 |
| 박스 무게 한도 | 없음 | 박스 기준정보에 무게 필드 없음. 도입 시 스키마 변경 — 별도 결정 |

### 4-7. 근거 (연구 대응)

- 문제 정식화: Multiple Bin-Size 3D Bin Packing. 편성과 적재를 한 문제로 푸는 근거
- extreme point 배치: Crainic et al. 2008 — 배치점 휴리스틱의 표준
- 슈퍼블록: 컨테이너 적재의 block-building 계열
- FFD 초기해 + 국소 탐색 개선: 메타휴리스틱 하이브리드의 축소판
- 상세 출처: 지식 저장소 `concepts/cartonization.md`

## 5. 라인 배정 [확정]

- 라인별 담당 지역 고정 매핑 (방면별 분류의 단순화). seed: 1라인=서울, 2라인=경기, 3라인=부산
- 같은 지역에 활성 라인이 여럿이면 라인 ID 오름차순 첫 라인 (결정적 임시 규칙). 배분 최적화는 차량 상차 기능과 함께 검토 — 2차 이연
- 지역에 활성 라인이 없으면 — 해당 주문 거부, 사유 `NO_ACTIVE_LINE` (2층 거부 목록 합류)

## 6. 토트 할당·저장·상태 전이 [확정]

- 배송단위 1개당 유휴 토트 1개 할당. 토트 부족 상황은 가정하지 않는다 — 발생 시 배치 전체 롤백과 500 (방어적 실패)
- 배치 전체 단일 트랜잭션. 거부 주문 제외는 트랜잭션 안에서의 분기이지 부분 커밋이 아니다
- 상태 전이: 주문 접수→할당완료, 배송단위 계획→토트할당, 토트 유휴→할당
